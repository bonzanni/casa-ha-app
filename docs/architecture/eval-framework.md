# The evaluation framework

> Code is the source of truth. This file is a map; when it and the code disagree, the code wins.

## Scope

What the evaluation framework is, and — more usefully — what it is not yet. This document is
short because the subject is small, and saying so is the point.

## Mental model

**The framework is scaffolding, not a working evaluation suite.** It defines a tester
abstraction and a registry, and **the registry ships empty.** No tester is registered, no
suite is defined, and nothing in the application or in CI invokes it. Its own module says so.

That matters mainly as a correction: the presence of an evaluation package invites the
assumption that behaviour is being evaluated somewhere. It is not. Test coverage in this
repository comes from the ordinary test suite, and that is where a behavioural guarantee
should be pinned today.

**Separate from the framework, some model-backed checks do exist**, and they are not wired
through it. Where they run a real model against a real composed prompt, they typically
substitute a fake for the expensive or irreversible tool — so they assert what an agent
*attempted*, not what happened. That distinction is worth carrying: passing means the model
asked for the right thing, not that the thing worked.

**Anything touching live memory uses a caller-supplied bank name.** Keeping evaluation away
from real memory is therefore a convention the caller must honour, not a guard the code
enforces. There is nothing that will stop a probe pointed at the wrong bank.

## Contracts & invariants

**INV-EVAL-001**: The tester registry is empty; no evaluator is registered or invoked.

Enforced by the fact that nothing calls the registration path. The contract tests assert
lookups fail, which is the current intended state.

**INV-EVAL-002**: Bank selection for any live-memory check comes from the caller; the code does not confine it.

Stated as an invariant because its absence is a real hazard: a mistyped or defaulted bank
name reaches whatever it names, including a real one.

## Failure behavior

**Requesting a tester.** Raises, because none is registered. This is expected behaviour, not
a broken installation.

## Extension points

**Adding a real evaluator** means implementing the tester interface and registering it — and
then deciding the things the scaffolding does not decide: what it runs against, how results
are reported, and whether it belongs in CI.

**Any evaluator touching memory** must select a disposable bank explicitly. Nothing will
prevent it addressing a real one, so that choice is the author's to get right.

**Before adding a check here**, consider whether it belongs in the ordinary test suite
instead. That suite runs; this framework does not.
